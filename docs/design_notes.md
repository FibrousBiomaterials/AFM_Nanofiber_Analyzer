# Design notes

Why the analysis modules and the bundle format are built as they are, and
what was measured when each decision was made. These passages were part of
`AGENTS.md` §8.2 and §8.7, which every agent session loads, and were moved
here unchanged so that file stays short; a passage that no longer described
the code has since been corrected. Read the notes of a module before
changing what it does. The code and its docstrings describe the current
behaviour; where a note and the code disagree, the code is right and the
note is out of date.

## Bundle format history (from AGENTS.md §8.2)

Format 1.1 is such a change — `kp` and `ka` are judged by
the excess-turning rule on the half-maximum centerline of `afm_nanofiber_analyzer/centerline.py`,
`dp` is written empty, and the optional `up` holds the bends not judged next to
a track end — and a reader builds a 1.0 bundle on its skeleton track, and
judges a fibril reconnected in it by the earlier polyline rule, until it is
re-analyzed (`bundle_schema.centerline_from_meta`). In 1.1 `ka` is the
interior angle between the arms read beside each bend
(`KinkDetector.judge_line`), and the excess each kink was judged by is
written to the optional `ke`, so the tested quantity travels with the arrays.
Format 1.1 had not been released when `ke` was added, so that definition was
folded into it rather than given a new version; a bundle labelled 1.1 without
`ke` came from the interim development code and should be re-analyzed. Format
1.2 is the next such change: the centerline is chosen per analysis
(`ProcParams.centerline_method`, one of `centerline.CENTERLINE_METHODS`) and
recorded in the required vlmeta entry `bundle_schema.CENTERLINE_KEY`, and every
reader builds fibers on exactly that line. No array changes, but a 1.1 reader
would build every bundle on the half-maximum line and draw kinks on a line they
were not judged on, so the version was bumped; a 1.2 bundle that names no known
line is refused rather than built on a guess. Format 1.3 places the line and
judges the kinks in physical geometry, with Y scaled by the pixel aspect of the
recorded scan size (`bundle_schema.pixel_aspect`), and never median-filters
`calibrated` (`apply_median` reaches only the image segmentation and
skeletonization read). No array changes, but a 1.2 reader would place a
non-square scan's line in pixel geometry beside kinks judged physically, so the
version was bumped; a reader builds a 1.2 or older bundle in the pixel geometry
it was judged in (`bundle_schema.pixel_aspect_from_meta`). Format 1.4 reads the
apparent width W at the level halfway between each cross-section's base and
the first maximum uphill from the track point (`centerline.WIDTH_PEAK_NEAREST`) instead of its overall
maximum, so a taller neighbouring fiber no longer sets the level a faint
fiber's width is read at, as long as the faint fiber has a maximum of its own. No array changes, but
`kp`, `ka`, `ke` and `up` were judged at that W and the line is placed with it,
so the version was bumped; a reader places the line of a bundle of format 1.1
to 1.3 with the overall maximum (`bundle_schema.width_peak_from_meta`). Format
1.5 reads W over a cross-section range that grows with the fiber
(`centerline.measure_apparent_width`): the fixed ±12 px took the base of a fiber
wider than about 10 px on the fiber's own skirt and read no fiber wider than
about 15 px. No array changes, but `kp`, `ka`, `ke` and `up` were judged at the
new W, so the version was bumped; a reader reads the width of a bundle of
format 1.4 or older over the fixed range
(`bundle_schema.width_range_adaptive_from_meta`). Format 1.6 searched for
bends down to a fixed excess turning of 10° instead of at the threshold and
stored the bends below the threshold in the optional `wp`, `wa` and `we`, with
the floor in the vlmeta entry `weak_bend_floor_deg`; `kp`, `ka`, `ke` and `up`
keep their shapes. Format 1.7 samples each
cross-section the line is placed on symmetrically about the track point and,
where the section rises on both sides, climbs to the nearer crest, and to the
higher one at equal distance (`centerline._climb_to_maximum`), instead of
preferring one side: tracing a fiber the other way reverses its normals, so the
one-sided rule moved the line, and every curvature and kink read from it, with
the direction the fiber happened to be traced in. No array changes, but `kp`,
`ka`, `ke`, `up`, `wp`, `wa` and `we` were judged on the new line, so the
version was bumped; a reader places the line of a bundle of format 1.6 or older
by the one-sided rule (`bundle_schema.symmetric_section_from_meta`). Format 1.8
stores none of `wp`, `wa`, `we` and `weak_bend_floor_deg`: no kink threshold is
applied to stored bends again, and a reader ignores them in a bundle of format
1.6 or 1.7.

## Module notes (from AGENTS.md §8.7)

### `bundle_schema.py`

Executable `.b2z` contract (§8.2). `pixel_size_nm` is the single place that converts a recorded scan size into the pixel size of the stored arrays (the stored count plus one, for the background calibrator's one-pixel trim); `afm_nanofiber_analyzer.measure`, the pipeline's ridge recovery and its scan-line-range crop all call it, because when each wrote out its own division, later code divided by the stored count and a cropped analysis measured Y lengths up to 2.7% short. `pixel_aspect` (Y pixel size over X pixel size, 1 without a scan size) is the geometry the centerline and the kink rule work in, and `pixel_aspect_from_meta` returns it for a format listed in `PHYSICAL_GEOMETRY_VERSIONS` (1.3) and 1 for older bundles, which were judged in pixel geometry; readers set `FiberTrackingImage.pixel_aspect` from it, never from a scale entered at measurement time. `width_peak_from_meta` likewise returns the width definition a bundle's kinks were judged with — `centerline.WIDTH_PEAK_NEAREST` for a format listed in `NEAREST_PEAK_WIDTH_VERSIONS` (1.4), `centerline.WIDTH_PEAK_GLOBAL` for older ones — and readers set `FiberTrackingImage.width_peak` from it. `width_range_adaptive_from_meta` returns whether W was read over a range that grows with the fiber (a format listed in `ADAPTIVE_WIDTH_RANGE_VERSIONS`, 1.5) or over the fixed ±12 px (older), and readers set `FiberTrackingImage.width_adaptive` from it. `symmetric_section_from_meta` returns whether the line was placed by the direction-independent climb of a format listed in `SYMMETRIC_SECTION_VERSIONS` (1.7) or by the one-sided rule of an older one, and readers set `FiberTrackingImage.symmetric_section` from it. Format 1.1 carries the optional `ke` (excess turning per kink, radians, one per `kp` column) beside `ka`, which is the arm angle, not 180° minus the excess. `APPARENT_WIDTH_KEY` names the optional vlmeta summary of the apparent widths the kink rule was scaled by (median, component count, fallback count), the scale a bundle's kinks were judged at. `PIXEL_LENGTHS_KEY` is deprecated: it names the record 2.0.x bundles carry of what the pixel-unit stage settings amounted to in nm, which the pipeline does not write and no reader uses, because `params` and `spatial_calibration` determine those values. keys, shapes, units, coordinate convention, format version, and the optional `spatial_calibration` vlmeta entry (scan size + source). `centerline_from_meta` says which line a bundle's kinks were judged on — the line recorded in `CENTERLINE_KEY` for a format listed in `CENTERLINE_KEY_VERSIONS` (1.2), raising `ValueError` when that entry is missing or unknown; the half-maximum centerline for a format listed in `HALF_MAX_CENTERLINE_VERSIONS` (1.1); otherwise the skeleton track — and every reader builds fibers on that line, so a bundle's stored kinks and its drawn line never come from two definitions. `validate_bundle` reports a 1.2 bundle whose `CENTERLINE_KEY` is not a known line. Imports the NumPy-only `afm_nanofiber_analyzer.centerline` for the line names. `PARAMS_KEY` names the vlmeta entry holding the `ProcParams` the analysis ran with, and `kink_params_from_meta` reads `kinkangle_deg` and `kink_decompose_px` back out of it. Those two are the only fields any reader *acts* on — `kink_decompose_px` only for a bundle of format 1.0, whose reconnected fibrils are judged by the earlier polyline rule — and they have to be: anything that recomputes kinks on a track the bundle does not contain — a reconnected fibril, a height-band sub-fiber — must apply the rule that produced `kp` / `ka`, and the bundle is the only place that rule travels with the arrays it explains. Deliberately not read from the `_param.json` sidecar, which is the analysis *input* and stays editable afterwards, so an edit there would change a fibril's kinks with no re-analysis. Each field is reported independently, and a missing or out-of-range one reads as "not recorded" (the caller then uses the `KinkDetector` default, which is what such a run used) rather than raising, because it is provenance written by an unknown release and refusing the bundle over it would block measurements that do not depend on it. Depends only on NumPy.

### `connect_selection.py`

Fiber-connection **result** recorded in `<stem>_connect.json` beside the bundle, written by GUI04's 「除外・連結を保存」 — which writes this file and the exclusion sidecar in one press, deliberately offering no way to write only one, because `curate_fibers` reads them together and a pair recorded at different moments describes a population that was never on screen (measured: 29 aggregated fibrils against 56 displayed fragments, unsignalled) — and applied by `measure.collect_fiber_stats(apply_connection=True)` and its three sibling collectors. It is the sibling of `fiber_selection.py` and now **the same kind of record**: both store an irreproducible human decision as data. Connection was stored as settings through the unreleased development version, on the ground that it is a deterministic function of the bundle and `ConnectParams`; that is true of the search but makes the *decision* depend on the population it runs over, so excluding a fragment could manufacture a join nobody chose — with `A-B-C` connected, discarding `B` re-ran the search and joined `A` to `C`, because `C` had become the only remaining candidate. Storing the result makes an exclusion able to cut a chain and never to extend one. What is stored is the **join structure, not the geometry**: one chain per fibril, each an ordered `ChainMember` list of `(anchor pixel, flip)`, and `build_connected_fibers` docks them again at measurement time. `resolve_plan_chains` turns each resolved chain to run from its lower-numbered fragment to its higher-numbered one, because the kink rule samples a fibril's line from its first point and the same fibril stored in the two directions — joined by hand from either of its fibers — would otherwise carry different kink angles. Storing the pixels instead would be the cache the settings design was avoiding — re-analyzing the bundle in GUI01 changes the skeleton, and a stored track keeps "working" while describing a skeleton that no longer exists, whereas an anchor matches no fragment and fails loudly. `skeleton_digest` makes that check immediate rather than waiting for the anchors to miss; `measure_bundle` refuses a plan whose digest does not match. Anchors follow `fiber_selection.fiber_anchor` and resolve uniquely because branch-point removal leaves the fragments disjoint. **Whether a join was automatic or manual is deliberately not recorded**: once the user has accepted a connection it is their decision either way, and a distinction nothing acts on would only invite code that acts on it. `CONNECT_PARAM_FIELDS` names are serialized verbatim and are frozen for the same reason `ProcParams` field names are (§8.1); a missing one falls back to its dataclass default. Of the six thresholds only `trim_points` and `num_avg_points` affect a fibril built from a stored chain — the other four gate the search — but all six are stored so GUI04 can search again with what the user tuned and so the run is auditable; `plan_state_key` therefore excludes them, or editing a threshold would light the save button over a change that cannot alter a number. The seventh field, `judge_bridge_kinks`, is the user's choice of whether a bend whose window reaches a connector bridge is judged; it changes the kinks of a stored chain's fibril, so `plan_state_key` includes it whenever a chain exists (only when it is off, so a plan at the default keys the same as one that does not record the setting), and it is read only as a JSON boolean. A file whose `version` exceeds `CONNECT_VERSION` is refused rather than parsed for the keys this version happens to understand, a file carrying one anchor in two chains is refused because it describes a fibril that cannot be built, and a malformed file raises instead of reading as "not connected", because falling back silently would measure fragments while the user believes whole fibrils were measured. A development file carrying `enabled` instead of `chains` is refused with an instruction to connect and save again: which fragments it would have joined is recoverable only by running the search, which is the thing this format exists to stop doing. Unlike `save_exclusions`, a plan with no chains writes the file instead of deleting it: a stale exclusion file would restore fibers the user rejected, whereas "nothing connects" and "no file" measure identically here, and keeping the file preserves both the tuned thresholds and the fact that not connecting was a decision. `load_connect_plan` returns `None` for a missing file, which is deliberately distinct from a stored empty result — GUI03 counts how many bundles carry a decision. `plan_without_anchors` dissolves whole fibrils, while `plan_without_junctions` cuts only the named junctions (pairs of adjacent members) and keeps the runs between cuts joined, which is what GUI04's connection list uses so one wrong join can be undone without taking the whole fibril apart. Depends on the standard library, NumPy, `fiber_connector.ConnectParams`, and `fiber_selection`'s anchor helpers.

### `fiber.py`

Immutable dataclass holding height, length, kink points, and endpoints per fiber. `width_px` / `width_measured` carry the apparent width the kink rule was scaled by and whether it was measured, `line_reliable` marks the points located on the fiber's own cross-section, and `height_measured` marks the height samples that are image samples rather than connector bridges; `measure.height_sample_mask` reads the last two. `xtrack` / `ytrack` are the line the fiber is drawn and measured along — the half-maximum centerline for a format 1.1 bundle, the skeleton pixel chain for an older one (`Fiber.centerline` says which) — and `skeleton_xtrack` / `skeleton_ytrack` hold the skeleton pixels it was traced from, one per line point. `unjudged_indices` marks the bends the kink rule measured and did not judge — within 1.5 apparent widths of an end, or at a connector bridge when the connection does not judge bridge bends — with the reason per bend in `unjudged_reasons` (`None` means every one is next to an end); they are drawn, never counted. `bridge_excluded_px` is the length of the judged span the bridges took, which `measure.fiber_kink_density` leaves out of its divisor. **Everything that identifies a fiber reads `skeleton_track`, never the drawn line**: exclusion and connection anchors, `fiber_track_pixels`, and the branch-point and frame tests. The skeleton moves only when the image is re-analyzed, which `skeleton_digest` detects, while the line moves whenever the centerline estimate changes, so keying identity on the line would silently detach existing sidecars.

### `centerline.py`

`place_centerline` is the full form: it returns the line as a `CenterlineResult` together with the apparent width W and whether it was measured or `FALLBACK_WIDTH_PX` was substituted, the per-point reliability (on a line placed on the cross-sections, an interpolated point lies on the frame, the skeleton track smoothed over W/4 (W/2 for `HALF_MAX_05W_CENTERLINE`), shifted by an interpolated offset, so a kink or curvature found there has the skeleton's shape, not the height's; the skeleton-based lines are the skeleton pixels, or the skeleton smoothed along its length, at every point), and the **crest height** per point — the value at the crest of the resolved cross-section, the first local maximum reached by climbing uphill from the reference-line point (not necessarily the maximum of the whole section read), or the height read at the line point when that is higher, which is what `Fiber.height` holds, because the line sits at the half-maximum midpoint and a height interpolated there reads low on an asymmetric section. `half_max_centerline` is the line-only wrapper of the default. The single definition of a fiber's line for each value of `CENTERLINE_METHODS`, which `place_centerline(method=...)` selects; the default, `HALF_MAX_025W_CENTERLINE`, is each traced skeleton point moved, along the normal of the smoothed track, to the midpoint of the two half-maximum crossings of the height cross-section, with sections that cannot locate the fiber (next to a branch point, two fibers side by side, a faint or foreign maximum) interpolated. The seven alternatives are the lines the default was chosen against (the half-maximum line at 0.5 W, skeleton pixels, skeleton smoothed over 0.5 W / 1 W, the quarter-maximum midpoint, the height centroid, the crest), kept selectable so the choice can be checked on the user's own images; they share the frame, the reliability tests (always at the half-maximum level) and the crest height, and differ only in where a point is placed. **Do not change the default without re-running the comparison in `docs/validation.md` §4.2–§4.3**: every result of a default analysis moves with it. `is_placed_line` separates the selectable lines from the format 1.0 `SKELETON_TRACK`, and `is_pixel_chain_line` marks the lines measured with the chain-code metric (`SKELETON_TRACK` and `SKELETON_PIXEL_LINE`). One point per skeleton point. GUI01's `KinkDetector` and `FiberTrackingImage` (when a bundle is opened) both call `place_centerline` with the bundle's method, so the stored kinks and the drawn line come from one computation; `fiber_connector` docks the fragments' existing lines rather than placing new ones. The frame and the offsets are smoothed over a quarter of the apparent width, not half: at half a width, same-sense corners 1–3 widths apart were judged as one bend in 2 of 8 synthetic scans, at a quarter width in 1 (`docs/validation.md` §4.2). **The half-maximum midpoint was chosen over the crest because a twisted fibril with an anisotropic cross-section swings its crest from side to side** (on 4 of 5 synthetic twisted ribbons the crest strayed farthest from the axis, and 0.99–1.48 times as far as the half-maximum midpoint), and over lower levels because those follow background bumps beside thin fibers; see `docs/validation.md` §4.2. Every length is a multiple of the apparent width, so nothing depends on the scan size. `measure_apparent_width` takes the half maximum of each profile from the first maximum the uphill climb from the track point reaches (`WIDTH_PEAK_NEAREST`), the same climb the line placement uses, so a taller neighbour does not set it as long as the fiber has a maximum of its own (a faint fiber that is only a shoulder on a taller one's flank climbs to that one), and a taller neighbour so close that the profile between them stays above the level still widens the run; `WIDTH_PEAK_GLOBAL` is the overall maximum a reader passes for a bundle older than format 1.4. The profiles are read over ±12 px first and, when that range is shorter than 1.25 W, again over 2 W (at most 96 px), a reading kept only when most of its sections hold a single crest, so a neighbouring fiber is not taken in; `adaptive_range=False` keeps the fixed range, which a reader passes for a bundle older than format 1.5. Covered by the §8.13 documentation rule. Depends only on NumPy.

### `fiber_connector.py`

**The search, the candidate lists and the docking read the fragments' skeleton pixels** (`fiber.skeleton_track`), so which joins are proposed does not depend on where the line is placed; the points the gates compare are scaled to specimen geometry by the pixel aspect (`_physical`), so `clusters_range` is in X pixels and the angles are the specimen's; a built fibril carries its fragments' own lines joined by straight bridges, index-aligned with the docked skeleton pixels, and `filter_fibers_by_height` cuts the parent's line instead of placing a new one. Reconnection is split into a **search** (`plan_from_auto_connect`, returning one `(fragment_index, flip)` chain per fibril) and a **construction** (`build_connected_fibers`, docking a chain into a `Fiber`); `connect_fiber_fragments` composes the two and is the convenience form for a caller with nothing to store. The split exists because the search is what cannot be repeated safely — it is sequential and population-dependent — while construction is a pure function of the chain, so recording the boundary between them is what lets a later measurement rebuild the fibrils that were on screen instead of searching again over a population that has meanwhile changed. Construction trims each junction by the **fragment's own length**, not by the length of the fibril grown so far, so the result does not depend on which end the search happened to grow from; verified bit-identical to the pre-split connector on two real scans (136 and 14 fragments). A fragment no chain claims is **passed through untouched rather than rebuilt**, so adding one join does not perturb every unrelated fiber in the image; measured on two real scans this changes no measured quantity (length, height median/max and kink count were identical) and corrects `EP count`, which rebuilding forced to 2 for fragments whose second end is a cut rather than a skeleton endpoint. `connection_candidates` backs GUI04's manual connection: it lists the ends within `MANUAL_RANGE_FACTOR` × `clusters_range` of one fiber's ends and **reports** the angle and height gates per candidate instead of applying them, because restricting the list to what the search accepts would let a manual connection only re-choose among joins the machine already considered, while the case that actually needs a human — a continuation the angle gate rejects — would be unreachable except by editing thresholds, which is the mode-like behavior a per-connection decision replaces. `connection_candidates_by_index` is the whole-population form GUI04 fills its candidate cache from, and both share one per-fiber scan so they cannot report different candidates. It exists because the end geometry and the per-fiber median heights describe the *population*, so calling `connection_candidates` per fiber rebuilds them `n` times over: measured on the tunicate test scan (60 fibers) that was 0.55 s against 0.015 s for the equivalent whole-population pass in `connection_candidate_flags`, and it grows as `n^2` on the Tk main thread. `chain_for_manual_join` concatenates two displayed fibers' chains end to end, reversing order and flips where the join is at a chain's head, so a fragment pair, an extension of a fibril, and the merging of two fibrils are one construction. `connection_candidate_flags` answers "could the connector extend this fragment?" as a **standalone, order-independent predicate over the original fragments** — deliberately not a record of what `connect_fiber_fragments` did, because that function consumes fragments as it grows, so which joins happen depends on the visiting order and a predicate used to judge a fiber cannot depend on it. It applies the same distance, angle, and height gates, evaluated on each fragment's own end, look-back direction, and median height, and flags **both** fragments of a joinable pair of ends (the connector's gate is written from the growing side and is not symmetric, so one orientation alone under-reports). Measured against what the connector actually joined on two real scans, it agreed on 145 of 146 extended fragments. Used by `measure.isolated_fiber_flags`, and **only in conjunction with the branch-point and frame tests** — alone it is about five times looser, because "no candidate" conflates "complete" with "the connector could not tell", which is the common case in a dense tangle. The search reconnects skeleton fragments split at crossings/branches into whole fibrils by local position/direction/height continuity, and construction rebuilds one `Fiber` per fibril (features recomputed via `KinkDetector`, which receives the bridges as the points whose height was not measured and judges a bend reaching one only when `ConnectParams.judge_bridge_kinks` is on; `filter_fibers_by_height` takes the same choice so a height-band piece is judged as its fibril was). Only GUI04 runs the search, when the user presses 「自動連結」; a measurement elsewhere applies the chains that press recorded. Sequential (order-dependent), so not parallelized. `filter_fibers_by_height` implements GUI04's "connect, then filter" order: it slices each already-built fibril by its own `Fiber.height` profile (bridge heights included, so an in-band bridge keeps the fibril joined) instead of masking the raw skeleton like `FiberTrackingImage.specific_height_fibers`.

### `fiber_selection.py`

Manual fiber exclusions recorded in `<stem>_excluded.json` beside the bundle, written by GUI04 and applied by `measure.collect_fiber_stats(apply_exclusions=True)`. An exclusion is an **anchor pixel on the excluded fiber's track, never a list index**: turning fiber connection on or off renumbers the fiber list, so a stored index would point at a different object, while a pixel keeps its meaning across tracing modes. A fiber is excluded when its track passes through any anchor. Clearing every exclusion deletes the file, so "no sidecar" always means "nothing excluded"; a malformed sidecar raises rather than reading as empty, because silently ignoring it would restore fibers the user rejected. A sidecar whose `version` exceeds `EXCLUSION_VERSION` is refused for the same reason and on the same terms as `connect_selection.load_connect_plan` — a later version could give an entry a meaning beyond "exclude the fiber through this pixel", and reading it as a plain point exclusion would measure a population nobody chose — while a file with no `version` key reads as the current version, so a hand-written sidecar still loads. The two sidecars are written together, so their readers must not disagree about what an unreadable file means. **Anchors are applied to the fragments before fiber connection** (`measure.curate_fibers`), so excluding a *connected fibril* must record one anchor per constituent fragment, not the fibril's own `fiber_anchor`: a fibril's midpoint lies on only one of the fragments it was built from, so a single anchor removes that fragment and lets the rest reconnect into a shorter fibril, partly restoring the object the user rejected and leaving it no longer matched by its own anchor. GUI04 reads the constituent fragments from the fibril's chain (`App._display_chains`), because `constituent_anchors`, which finds them by overlap — a fragment counts when more than half its track lies on the displayed fiber, so a fibril merely crossing another fragment in a dense region does not drag it in — misses a short fragment trimmed at both of its junctions. GUI04 does not exclude while its height filter is on: a row is then a piece of a fiber, and an anchor names a whole fragment. Anchors and track pixels are the **skeleton pixels** a fiber was traced from (`fiber.skeleton_track`), never its drawn line, so a sidecar written before the half-maximum centerline still matches after re-analysis. Depends only on NumPy and `afm_nanofiber_analyzer.fiber`.

### `group_compare.py`

Between-group comparison of collected samples, used by GUI03: two-sided Mann-Whitney U and two-sample KS with Holm correction across all pairs, plus Cliff's delta as a sample-size-independent effect size. Both tests are rank-based because fiber morphology distributions are right-skewed. GUI03 takes Mann-Whitney U as the primary test and shows the KS p-value uncorrected as a reference, because reading whichever came out smaller tests each pair twice; `PairComparison` and the comparison CSV keep the Holm-corrected KS value. `cliffs_delta` derives the effect size from the U statistic rather than counting pairs, which would be quadratic. **The caller owns the independence assumption**: GUI03 offers these only for its `fiber` and `image` aggregation units, because skeleton pixels are not independent observations and a p-value over them measures the sampling density rather than the specimen. Fibers of one image share that scan too, so the `fiber` unit counts as independent what the `image` unit does not, and GUI03 says so under the comparison table for the `fiber` unit. A pair whose values can be split between the two groups in at most `_EXACT_ARRANGEMENT_LIMIT` ways is tested by counting every split, exact with tied values too, because scipy's Mann-Whitney turns to its normal approximation on tied values and gave three equal values against three others p = 0.047, below the 0.10 such a pair can reach. A larger pair with tied values and at most `_SAMPLED_MAX_VALUES` values is tested on `_SAMPLED_SPLITS` random splits with a fixed seed, so its p-value cannot read below `1 / (1 + _SAMPLED_SPLITS)`, because scipy's KS test stays conservative on tied values at every size. Above that many values, and on untied pairs, scipy is used; its KS p-value there is conservative on tied samples. Imports `scipy.stats` inside its functions, per §8.5.

### `fiber_tracking_image.py`

GUI04 data container; builds `Fiber` instances from a `.b2z` bundle, on the line its `centerline` attribute names: the recorded line of a format 1.2 bundle or the half-maximum centerline of a format 1.1 bundle (`centerline.place_centerline`, given the branch-point mask so junction neighbourhoods are interpolated), the skeleton track for an older one. `afm_nanofiber_analyzer.measure` sets the attribute from the bundle (`bundle_schema.centerline_from_meta`); a container built by hand defaults to the skeleton track. `unjudged_point_coordinates` carries the optional `up` key into `Fiber.unjudged_indices`, and is empty for a bundle that lacks it. Also carries `kink_angle_deg` / `kink_decompose_px`, the thresholds the stored kink points were detected with, which `afm_nanofiber_analyzer.measure` fills in from the bundle. They live on the container rather than being passed per call because every consumer that recomputes kinks already holds the image, and one that has to be told separately is one that can be told wrong — which is exactly what happened: `fiber_connector` recomputed a reconnected fibril's kinks at the hard-coded `KinkDetector()` defaults, so a scan analyzed at any other angle showed two rules at once. `None` means the bundle records no usable value and the detector default applies, which is what such a run used.

### `gwy_convert.py`

Converts files this software cannot read into `.gwy` by running `gwyconvert` from the optional `convert` dependency (`gwyddionpy-converter`) as a separate process; shared by GUI00 and `cli.py convert`. Selection is by extension alone (everything except `SKIPPED_EXTENSIONS`, the inputs read directly and the files the project writes), the output is `<input file name>_converted.gwy` beside the input (`CONVERTED_SUFFIX`): the input's extension keeps `scan.000` and `scan.001` apart, and the suffix keeps the output from sharing a bundle name with a text export of the same scan, because GUI01 drops only the last extension and instruments name text exports after the raw file (`scan.ssp.txt` and a plain `scan.ssp.gwy` would both become `scan.ssp.b2z`), and an input whose output exists is reported as `STATUS_EXISTS` without running the converter. A result is kept only when it holds a length-unit channel, because Gwyddion also opens ordinary images (a PNG becomes a unitless channel one metre wide) that would otherwise be analyzed as height maps. The converter writes into a temporary folder inside the output folder and the result is moved into place only after that check, so a failed run never leaves a `.gwy` under the final name, which every later run would skip as converted. `gwyddionpy_converter` is imported only inside `find_converter`, to locate the executable, because the converter is GPL: it never enters this process and is excluded from the frozen build (§8.6). `INSTALL_COMMAND` names the same requirement as the `convert` extra, which `tests/test_gwy_convert.py` checks. Imports `gwy_io` to read the result back.

### `gwy_io.py`

Reads Gwyddion native `.gwy` files (binary, multi-channel). Callers test for a `.gwy` path inline (`os.path.splitext(path)[1].lower() == ".gwy"`) rather than through a helper here, and must keep doing so: `gwy_io` imports from `afm_io`, so `afm_io` cannot import `gwy_io` at module level, and `afm_io` / `pipeline` deliberately run the test *before* the lazy `from . import gwy_io` so a text-only workflow never loads the module. A predicate living here is unreachable from the three places that need it, which is why `is_gwy_path` was removed rather than adopted. `load_gwy_image` returns the selected channel's height matrix in nm plus its scan size (µm); `select_default_channel` auto-selects the topography/height channel, overridable by id or title. Imports the optional `gwyfile` package lazily inside its functions; reuses `afm_io.ScanSize`.

### `kink_detector.py`

Searches for candidate bends down to the fixed excess turning `_SEARCH_FLOOR_DEG` (or the threshold, when that is lower) and discards those that miss the kink level, and shuts out a window-turning candidate only by a stronger curvature-maximum candidate; arms are cut only at bends reaching the kink level. Judges kinks on each traced component's centerline (`centerline.place_centerline` with `KinkDetector.centerline_method`, the half-maximum centerline by default), not on its skeleton pixels, by the **excess-turning rule** of `KinkDetector.judge_line` (`kinks_on_line` is its tuple form): a bend is a kink when its turning within ±0.75 W, less what the fiber's own curvature on the flanks accounts for, reaches 180° minus `kinkangle_deg`. The angle it *reports* is the interior angle between the arms read beside the bend (beyond the half width the probe rounds the apex over, cut short at the next bend), not 180° minus the excess, which read low on sharp corners; the excess is returned beside it (`KinkJudgement.kink_excess`, bundle key `ke`) because it is the quantity that was tested. `NOISE_SIGMAS` gates a per-line noise floor of the excess (robust scale of the excess along the whole line); it ships at 0 because on the visual reference the floor removed clear kinks at about half the rate it removed false detections — the false detections are rounded bends and tangles, not noise — and it inflates on a heavily bent fiber, whose own kinks raise its floor. Do not turn it on without re-scoring `scripts/kink_reference_score.py`. Every length is a multiple of the apparent width W, so nothing depends on the pixel size; changing any one length to a neighbouring value kept the clear kinks found on the bundled scans' visual reference between 48 and 51 of 53, so do not tune one to a fiber. A bend within 1.5 W of an end is **not judged** and is returned separately (bundle key `up`, `Fiber.unjudged_indices`), so GUI04 can show it without counting it — neither fold it into the kinks nor drop it, because "not judged" must stay distinguishable from "measured and below the threshold". `judge_line` also takes the bridges of a connected fibril (`observed`) and the user's choice (`judge_bridges`): with the choice off, a bend whose window reaches a bridge is returned unjudged with the reason `UNJUDGED_AT_BRIDGE` (the other reason is `UNJUDGED_NEAR_END`, `KinkJudgement.unjudged_reasons`), and `KinkJudgement.bridge_excluded_px` reports the length of the judged span the bridges took. A bundle never holds a bridge bend, because the analysis that writes it does not connect fragments; bridges exist only in fibrils built from a connection plan, which GUI04, GUI03 and `afm_nanofiber_analyzer.measure` given a plan do. On the skeleton track of a format 1.0 bundle a reconnected fibril is judged by the polyline rule, without bridge handling. Kinks are stored at the skeleton pixels of the same indices, so no bundle array changes shape, and `dp` is written empty. `kinks_and_decomposed_from_track` keeps the earlier polyline rule only for bundles of format 1.0, whose reconnected fibrils must be judged by the rule that produced the rest of the image; it is the only reader of `threshold_distance` (`kink_decompose_px`). Requires `calibrated_image`.

### `measure.py`

GUI-independent fiber measurement shared by GUI03, GUI04, and `cli.py measure` / `heights`; keeps GUI and CLI statistics identical. `length_floor_nm` is a bundle's shortest fiber length kept at any angle, `max(h_length, area_min / W)` pixels at the larger pixel size; GUI03 warns when the bundles pooled in one group have floors more than 1 % apart and cuts nothing: cutting a group at its longest floor would discard the short fibers its finer scans do record. Groups are not compared for it, because each specimen may be imaged at the resolution its fibers need, and skeleton-pixel heights, which measure no fiber length, are not checked. `height_sample_mask` is the single definition of which height samples a fiber's statistics use — the crest heights less the last `CUT_END_EXCLUSION_WIDTHS` at a cut end (the other fiber's skirt at a crossing extends about a width past the 3×3 `remove_bp` clears) and less the connector's interpolated bridges with the same width on either side of them, since a bridge spans such a crossing — and GUI04's profile draws the excluded samples dashed and reads its guide lines from the same mask. `skeleton_height_values` does not use it: it reads skeleton pixels without tracing (below). `fiber_kink_density` divides by the **judged** length (contour less `kink_detector.END_MARGIN_WIDTHS` × W at each end and less `FiberStats.bridge_excluded_nm`, the bridges of a connected fibril and, when bridge kinks are not judged, the positions whose window reaches one); only a fiber without a width — the skeleton track of a format 1.0 bundle, or a CSV row without `apparent_width_nm` — is divided by its whole contour. `FIBER_CSV_COLUMNS` only ever grows by appending, so every earlier set is a prefix and `read_fiber_csv` accepts all of them. Its last three columns record the scan sizes the lengths were measured at and `MeasureResult.scale_source` (`SCALE_SOURCE_RECORDED` when they equal the bundle's recorded scan size, `SCALE_SOURCE_ENTERED` otherwise), which `measure_bundle` sets and GUI04 and `cli.py measure` pass to `write_fiber_csv`, so a file says whether its lengths are reproducible from the bundle alone; they are not part of `FiberStats`. `FiberStats.frame_end_count` counts the fiber's skeleton endpoints that lie on the frame, disjoint from `cut_end_count`, so `fiber_real_end_count` can say how many ends are the fiber's own; `kaplan_meier_length_weights` turns those counts into the Kaplan-Meier estimate of the length distribution behind GUI03's `Kaplan-Meier` frame mode, counting each own end as one observation that starts at a fiber end (two for a fiber seen whole, one censored for a fiber cut at its other end, none for a fiber with no own end), with weights that count fibers, so estimates made separately can be pooled; `docs/validation.md` §6.3 checks it against cut random segments. `measure_bundle` resolves the pixel size per axis (X from image width, Y from image height) so rectangular scans and non-square pixel grids are measured correctly; it defaults both axes to the bundle's recorded scan size when `scale_um` / `scale_y_um` are omitted, and a single `scale_um` keeps a square scan. `curate_fibers` is the **single owner of the order in which the measured population is built**: manual exclusions are applied to the traced fragments, and only then is the recorded connection plan applied to the survivors. No search runs there: a chain whose member was excluded is **split, not discarded** (discarding would delete the real fibers around a speck of debris) and never re-derived, which is what stops an exclusion from creating a join nobody chose. `measure_bundle` delegates to it, takes `exclude_anchors` for that purpose and `plan` for the connection, and refuses a plan whose `skeleton_digest` does not match the bundle; `MeasureResult.fragments` carries the uncurated fragments back so GUI04 can rebuild the population after an exclusion change without tracing again, and `MeasureResult.curated_count` reports how many fibers entered reconnection, so the difference from the fiber count is the number of joins the connector made — GUI04 logs it, because otherwise a run that joined nothing is indistinguishable from one that joined everything. Applying exclusions after connection instead deletes real fibers: an anchor matches any fiber whose track passes through it, so a discarded speck of debris that the connector had joined onto a real fibril took the whole fibril with it (on a test scan, five debris fragments discarded close to four times their combined contour length). **The height filter deliberately keeps the opposite order** — connect, then filter, see `fiber_connector.filter_fibers_by_height` — because it selects a height band *inside* a real fibril, which only has a meaning once the fibril is whole; exclusion instead asserts the object is not a fiber at all, so the connector must never see it. `isolated_fiber_flags` backs GUI04's "非孤立を除外" button and answers **"was this fiber measured over its whole length?"**, which takes three tests, not one: no track pixel within `BRANCH_TOUCH_RADIUS_PX` of a branch point, no track pixel on the outermost row or column, **and** no connection candidate (`fiber_connector.connection_candidate_flags`, using the `connect_params` the caller passes so the filter and the connection feature agree on what a continuation is). A fiber reaching the frame continues outside the scan, and the branch-point test cannot catch that on its own — there are no branch points beyond the frame, so a fiber running off the edge looks *more* isolated, not less. The frame carries no margin: measured on two real scans the count of fibers reaching it was identical for margins of 0 through 5 pixels, so a fiber that leaves the scan reaches the very edge. Only GUI04 calls this, so `cli.py` and GUI03 see it only through what GUI04 saves. **It is evaluated once, when the button is pressed, and its verdict is recorded as manual exclusions** (`note: "not isolated"`) rather than re-derived whenever a view is drawn. It was a checkbox filter through 1.0.0, and re-deriving it applied it to whatever list the views held: with the height filter also on, that was the sub-segments `filter_fibers_by_height` cuts out of a fibril, whose ends are the filter's cuts rather than the fiber's own. Measured on the tunicate test scan, the two filters together reported 26 "isolated" objects out of 137 segments — 22 of them pieces of a fiber the height filter had cut apart, 2-15 track pixels long — against 1 of 61 for the fibers themselves. Deciding once also lets the height filter run *on* the isolated population, which making the two filters mutually exclusive would have forbidden. Do not turn it back into a view filter. Two further properties follow from the verdict being taken once: it is **population-dependent**, because `connection_candidate_flags` compares each fiber against the others in the list it is given (dropping one fiber in turn flipped other fibers' candidate flags 18 times on the tunicate scan and 35 on the NDTOC scan, and their isolation verdict twice on the latter), and the branch-point test reads `image.bp`, which exclusions never rewrite — so of the three tests only the candidate test responds to a fiber being excluded. **On a dense specimen the conjunction can leave almost nothing** — 1 of 61 fibers on the tunicate test scan, and inspecting that survivor showed it to be a fragment between two crossings the connector could not resolve. That is the honest answer for such an image rather than a defect to tune away: do not loosen a test to make the count larger. `collect_fiber_stats` is the multi-bundle wrapper of `measure_bundle` and the per-fiber counterpart of `skeleton_height_values`: it shares that failure contract (an unreadable or scan-size-less bundle becomes an error entry instead of aborting) and returns results per bundle, because whether one sample is one fiber or one image is the caller's decision. **`skeleton_height_values` reads the calibrated image at the skeleton pixels, without tracing and without a centerline.** It leaves out only the pixels whose height is not one fiber's: the 3×3 around each stored branch point (what `imp_tools.remove_bp` clears; the stored `bp` is `branchedPoints` of the stored skeleton) and the skeleton closer to it than `CUT_END_EXCLUSION_WIDTHS` times the recorded median apparent width, measured along the skeleton, where the other fiber's skirt still raises the height (`docs/validation.md` §4.11). A manual exclusion drops the piece of skeleton holding its anchor; a connection changes no sample, because it adds only interpolated bridge heights. The 10-pixel area filter of `remove_bp`, L-corner removal, dropping components that cannot be traced and the minimum-sample fallback of `height_sample_mask` serve per-fiber measurement and are **deliberately not applied** to the pooled heights: none of them is a reason to drop a pixel's height. It needs no scan size, so it is the one combination GUI03 offers for pre-contract bundles. Every pixel counts once, so a fiber weighs in proportion to its pixel count and a finer pixel size weighs more; GUI03 warns when a group pools bundles of different pixel sizes rather than reweighting. `collect_skeleton_height_profiles`, the length-weighted counterpart that weighted each traced point by the contour length it represents (`contour_length_weights`), is deprecated: counting skeleton pixels already weights a fiber by its length, and GUI03 no longer offers the weighted unit. `read_fiber_csv` / `collect_fiber_stats_from_csv` read `write_fiber_csv` output back into `FiberStats` (no GUI reads a fiber CSV: a population curated in GUI04 reaches GUI03 through the two sidecars); both collectors take `apply_exclusions` (default `False`, so an existing sidecar never silently changes what `cli.py measure` reports). The bundle collectors — `collect_fiber_stats`, `collect_fiber_curvature`, `skeleton_height_values` — also take `apply_connection`, which honors each bundle's `connect_selection` sidecar with the same default and for the same reason. The tracing collectors resolve both sidecars through the single private `_curation_for`, so "apply the saved curation" cannot come to mean different things in different collectors; the **order** the two are applied in is not decided there but in `curate_fibers`. `skeleton_height_values` reads only the exclusions, because a connection changes none of its samples. A bundle without a connection sidecar is measured as fragments rather than refused, so a group can be curated one bundle at a time — GUI03 reports how many bundles in each group carried settings, because a partially curated group is otherwise invisible in the result. Uniformity of curation across compared groups is deliberately **not** enforced: `ConnectParams.clusters_range` is in pixels, so the same value is a different physical gap at a different scan size. Of a `_param.json`, GUI03 warns when the compared bundles differ in `centerline_method`, for any quantity, or in `kinkangle_deg`, for kink density, because those define what is measured, and still runs the test; other settings are not compared. On the half-maximum centerline (format 1.1) `FiberStats.straightness` is the Euclidean chord over the contour length, which is itself a Euclidean polyline length (0.9994 on a synthetic straight fiber), and the branch-point and frame tests of `isolated_fiber_flags` read the skeleton pixels (`fiber.skeleton_track`) they were measured on. On an older bundle's skeleton track, `FiberStats.straightness` is the length of a digitised straight line between the fiber's endpoints divided by its contour length, **both measured with the same corrected chain-code metric**: a Euclidean chord over that metric reads about 1.055 for a straight fiber, so measuring the reference line the same way is what makes 1.0 mean straight. It needs the pixel size and is NaN without it. Adding it extended `FIBER_CSV_COLUMNS`; `FIBER_CSV_COLUMNS_V1` is the 1.0.0 column set and `read_fiber_csv` accepts either, leaving straightness undefined for the older one, so a CSV exported with the earlier set still reads. `fiber_curvature_profile` needs a window because a skeleton step is orthogonal or diagonal only, so pixel-scale turning angles are quantised to multiples of 45 degrees: against arcs of known radius a 20 nm window returned 19.4 rad/µm whatever the true curvature, while 100 nm and above settled to a consistent 13-19% low. **That residual is the contour-length metric over-measuring strongly curved digitised paths** (+15-21% at 1.5 rad of total turn, +0.8% at 0.15 rad); the turning angle itself is exact. A larger window drops every fiber shorter than it, so raising it changes the population and GUI03 logs how many fibers it excluded. `fiber_mean_curvature` is the single definition of one fiber's curvature; `collect_fiber_curvature` and GUI04's fiber table both call it, so a value checked against the rendered fiber in GUI04 is the value GUI03 histograms. `fiber_kink_density` (kinks per micrometer of `fiber_judged_length_um`, a real 0 without a kink) is the value GUI04 shows per fiber; GUI03 compares kink density per `image` only, dividing the pooled kink count by the pooled `fiber_judged_length_um` instead of taking a median of per-fiber densities, which is 0 whenever more than half the fibers carry no kink, because one fiber's density takes the values 0, 1/L, 2/L... of its judged length L, so a per-fiber distribution is shaped by the fragment lengths. `fiber_kink_angle` is a deprecated alias (removed in 3.0.0) of the private `_fiber_kink_angle`, for the reason below: GUI03 does not compare kink angles. **Every quantity GUI03 can histogram has a GUI04 fiber-table column**, because GUI03 shows them only pooled into a distribution, where a wrong value is invisible; the user checks a value by reading it beside the fiber it came from. Adding a GUI03 quantity means adding its GUI04 column, which `test_gui04_fiber_table_covers_every_gui03_quantity` enforces. Kink angle is the recorded exception: a cell holds one number, but the kinks along a fiber are **distinct defect events, not repeated measurements of one fiber property** the way height pixels are, so a per-fiber median of them is not a property of the fiber — and for most fibers it degenerates anyway (27 of 37 fibers in the tunicate test image carry zero or one kink). The individual angles reach the user through the CSV, which stores all of them. Before adding a quantity to either GUI, apply the test in the `orientation order`/`network density` note above: is it a scientifically meaningful parameter of a nanofiber? An orientation order parameter and a network density were each implemented and then removed. **The test a quantity must pass is whether it is a scientifically meaningful parameter of a nanofiber** — whether it corresponds to a property of the fibril that nanofiber research asks about. Contour length, height, straightness, curvature, and kink geometry do: they describe an individual fibril's dimensions and shape. Alignment and areal coverage are meaningful for oriented films, mats, and nanopaper, where the network itself is the object of study; here the object of study is the individual fibril, dispersed and drop-cast onto the substrate, so neither answers any question about it. Do not adopt a quantity from comparable software (FiberApp, CT-FIRE, OrientationJ) without first checking it against what this project studies.

### `pipeline.py`

GUI-independent preprocessing driver shared by GUI01 and `cli.py process`; owns `ProcParams` (field names frozen, §8.1) and stage construction. `background_warnings` compares a finished analysis with the limits each background method was checked to on zoomed copies of the bundled scans (`docs/validation.md` §1.8): every length the methods use is a pixel count, so fibers spread over many pixels lose height to the background. `process_file` returns the warnings in `PipelineResult.background_warnings`, which GUI01 logs and `cli.py process` prints with the setting to analyze again with. Those limits are predictions from the measured apparent width; beside them the check measures the calibrated image itself (`_absorbed_fraction`: the share of the fibers' relief subtracted as background standing above the background beside the fiber mask) and, when no width could be measured for most components, says so (`"width_unmeasured"`) instead of returning nothing, because a calibration that removed the fibers leaves exactly that state; `docs/validation.md` §1.10 records how both kinds fared. `noise_warnings` is the second check `process_file` returns (`PipelineResult.noise_warnings`, logged by GUI01 and printed by `cli.py process`): it warns when the median calibrated height under the skeleton is less than `MIN_FIBER_SNR` times the pixel noise of the calibrated background (`fiber_snr`), because a crest height is the largest of noisy samples and noise also defeats the single-crest test a wide fiber's width is read with; the limit was set on synthetic fibers (`docs/validation.md` §4.15–§4.17). It names no setting to rerun with, because no analysis setting removes pixel noise. `BG_METHODS` and `canonical_bg_method` are re-exported from `bg_calibrator`; `merge_params_dict` applies the alias translation so every file-load path normalizes `bg_method`.
